# Architecture

## Boundaries

The backend starts as a plain JavaScript Node.js modular monolith. Each feature
owns its Mongoose model, validation schema, service, controller, and routes. React
components use JSX. This keeps deployment simple while preserving boundaries if a
module later becomes a separate service.

```text
React web app
    |
    | HTTPS / JSON
    v
Node.js / Express REST API
    |
    +-- member
    +-- subscription
    +-- payment          (future)
    +-- gymclass         (future)
    +-- reminder         (future)
    +-- assistant        (future)
    |
    v
MongoDB
```

## Collections

### `members`

Stores profile and contact data. Email has a unique index.

| Field | Type | Notes |
| --- | --- | --- |
| `_id` | ObjectId | Generated by MongoDB |
| `firstName` | string | Required |
| `lastName` | string | Required |
| `email` | string | Required, normalized to lowercase, unique |
| `phone` | string | Required, international format recommended |
| `status` | enum string | `ACTIVE`, `INACTIVE`, `SUSPENDED` |
| `joinedAt` | BSON Date | UTC instant |

### `subscriptions`

Stores subscription history separately from member profiles. Mongoose persists
JavaScript `Date` values as BSON dates. `memberId` and `endDate` are indexed for
member history and reminder queries.

| Field | Type | Notes |
| --- | --- | --- |
| `_id` | ObjectId | Generated by MongoDB |
| `memberId` | ObjectId | Reference to `members._id` |
| `planName` | string | Display name of the plan |
| `startDate` | BSON Date | UTC instant |
| `endDate` | BSON Date | UTC instant, indexed |
| `status` | enum string | `PENDING`, `ACTIVE`, `EXPIRED`, `CANCELLED` |
| `amount` | Decimal128 | Avoids floating-point money errors |
| `currency` | string | ISO 4217 code such as `INR` |

References use explicit ObjectId values rather than DBRefs. Cross-collection
consistency belongs in the subscription service.

## API conventions

- Base path: `/api/v1`
- JSON request and response bodies
- Zod validation at controller boundaries
- Thin controllers; business rules live in services
- RFC-style structured errors
- Conflict response for duplicate email addresses
- UTC dates across API and persistence

## Delivery roadmap

1. **Foundation:** member create/list, MongoDB models, and member list UI.
2. **Complete CRUD:** update/delete, pagination, filtering, forms, and tests.
3. **Subscriptions:** APIs, plan rules, end-date calculations, and indexes.
4. **Security:** Express authentication middleware, staff/member roles, password
   hashing, short-lived JWT access tokens, refresh-token rotation, and protected
   routes.
5. **Automation:** a scheduler queries an exact UTC/local-time window, writes
   idempotent reminder jobs, and sends approved WhatsApp templates.
6. **Payments and classes:** provider-neutral payment records and capacity-aware
   class booking.
7. **AI assistant:** backend-only LLM credentials, curated gym policy context,
   health-advice safety boundaries, rate limits, and auditable conversations.

For reminders, a production implementation should persist a uniquely keyed
reminder job before sending. That prevents duplicate messages after restarts or
concurrent scheduler execution.
